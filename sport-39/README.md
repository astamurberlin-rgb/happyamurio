- `sport/src/local-store.js` — `SportLocalStore`: синхронный фасад `sportStorage` (`getItem/setItem/removeItem/key/length`) над кэшем, который загружается **до** запуска приложения (`profile-lock.js` ждёт `SportLocalStore.open()` и для обычного старта, и для встраивания замеров); записи уходят в IndexedDB по очереди, `flush()` ждёт их фиксации. - Миграция при первом открытии: ключи Sport из localStorage копируются в IndexedDB, читаются обратно и сравниваются; только после этого удаляются из localStorage, и ставится маркер `auth-readonly-happy-sport-prototype-v1:indexeddb-v1`. Ключи, уже лежащие в IndexedDB, не перезаписываются старыми копиями. Любая ошибка — остаёмся на localStorage, ничего не удалено, причина в диагностике.
- Движок синхронизации (`controlled-cas.js`, `controlled-journal.js`) перед отправкой в сеть ждёт `flush()`: маркер попытки записан на диск до того, как что-то уходит с устройства. Отказ IndexedDB при записи приходит как `storage_quota`.
- Уведомления между вкладками — `BroadcastChannel('happy-sport-store-v1')` (событие `storage` для IndexedDB не приходит); другая вкладка перечитывает изменённый ключ.

## Что нового

- **Общие счётчики Meal ↔ Day ↔ Sport.** Счётчик продукта, у которого в Meal включена связь «Happy Sport», показывается в Дневнике Sport; нажатия «+»/«−» создают отдельные порции и расходятся по трём приложениям через аккаунт Happy. Документ тот же, что у Meal и Day: локальный ключ `happy-food-counters-v1:<uid>`, зашифрованная строка `app_sync` app=meal, kind=counters. Документ Update 37 под ключом `auth-readonly-happy-food-counters-v1:<uid>` читается один раз как отправная точка и не удаляется.
- **Узкий канал записи счётчиков** в `sport/src/readonly-guard.js` (`bindCounterController`): фиксированные URL, метод и заголовки, условная запись по `at`+`iv`, лимит размера, одна запись за раз. Все прочие записи по-прежнему запрещены; канал журнала не менялся. Копия счётчиков **не входит** в облачный журнал `sport/journal` — иначе каждая отметка в Meal создавала бы ложные конфликты журнала между устройствами.
- **Структура настроек**: Аккаунт → Приложение (Библиотека, Таймер, Датчики, Иконки) → Данные (Мои данные, Резервная копия, Облачная копия) → Связанные приложения → «Для разработчика» (скрыт) → История обновлений и версия. Раздел для разработчика открывается долгим нажатием (1,2 с) на строку версии и содержит служебные проверки синхронизации, резерв синхронизации, диагностику сборки и перенос истории Strong. Реализовано последним слоем `sport/src/settings-layout.js` поверх прежних экранов; блоки не переписаны, только перегруппированы.
- Кнопки «Happy Day» и «Happy Meal» ведут на опубликованные `day-52/` и `meal-23/` того же origin. Единые названия: «Выгрузить дневник», «Загрузить дневник», «Вернуть дневник до загрузки».

## Сборка и проверка

Из этой папки:

```sh
node scripts/build-release.mjs
npm --prefix sport run check
node scripts/check-settings-layout.mjs   # структура настроек в headless Chrome; пропускается без Playwright
node scripts/write-provenance.mjs        # после финальной сборки

```

Из корня репозитория дополнительно: `node scripts/check-food-counters.mjs` (общий модуль счётчиков: корневая копия, эталон `day-52/shared/food-counters.js` и совпадение копии этого выпуска с эталоном), `node scripts/check-layout.mjs`, `node scripts/check-shared-ui.mjs`.

Сборщик обновляет только файлы внутри этого выпуска. В Git входят исходники и корень выпуска; промежуточные результаты (`dist/`, `sport/dist/`, `sport/sport-icons/` и другие копии в `sport/`) перечислены в корневом `.gitignore` и создаются сборкой заново — поэтому на свежей копии репозитория сначала `node scripts/build-release.mjs`, затем проверки. Контрольные суммы всех включённых файлов и происхождение — в `SOURCE-PROVENANCE.json` (только закоммиченные файлы). Все данные в автоматических проверках искусственные; личные выгрузки не входят в код или публикацию.

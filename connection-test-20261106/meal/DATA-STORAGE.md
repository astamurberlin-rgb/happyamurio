## Актуализация 31.10.2026 · Meal 22.11-test.17 (только тестовый Sites)

Полный журнал Meal теперь синхронизируется через существующую `app_sync`,
`app=meal, kind=journal` с UID владельца и прежним AES-GCM. Политики доступа,
схема и ключи аккаунта не изменены. Историческое описание ниже относится к
прежним выпускам; Day и полный журнал тренировок этим изменением не затронуты.

Новый документ хранит записи по глобальному ID, отдельные ревизии порядка,
настройки, рецепты и использованные составы. Локальные маркеры удаления и
write-ahead patches переживают отсутствие сети/перезапуск и объединяются перед
каждой отправкой. Серверная запись условная по IV прочитанного документа;
пустой новый клиент сначала получает историю. Одновременные правки одной записи
выбираются по ревизии и идентификатору автора; независимые записи сохраняются.

Большие журналы и копии перед импортом хранятся в IndexedDB `happy-meal-private-v1`
по прежнему физическому ключу профиля. Чтение старого window.storage/localStorage
сохранено до первой миграции; после маркера миграции отсутствующая база вызывает
ошибку, а не подмену устаревшим резервом. Ошибка чтения при запуске блокирует
пустую перезапись. Транзакция записи объединяет ревизии предыдущего документа,
защищая от устаревшей вкладки. localStorage содержит только небольшие маркеры
и отдельные незавершённые операции, не многомегабайтный полный журнал.

JSON-дополнение и подтверждённые замена/отмена проходят через тот же механизм.
Не удалять старые иконки до проверки миграции: данные старого домена не появляются
на сервере, пока обновлённая версия на нём их не отправила или пользователь не
перенёс частный JSON. Эта публикация не импортирует персональные файлы.

Статус «Полный журнал синхронизирован» появляется только после подтверждённой
записи/сверки сервера. Ошибка чтения/ключа никогда не запускает замену вслепую.
Сжатый журнал требует CompressionStream/DecompressionStream (актуальный браузер).
Данные сохраняются по владельцу; переподключение другого аккаунта требует
перезагрузки. Закрытое приложение не синхронизирует. Старые сборки без этого
модуля по-прежнему не читают полный журнал. Реальный iPhone ещё не проверен.

## После обновления

Перенос сохраняет существующий формат и адреса хранения записей.
В том же браузерном хранилище новые страницы должны читать прежние записи.
Другой домен, браузер, устройство или установленная иконка могут использовать
другое хранилище. До удаления старой иконки проверить дневник на новом адресе.
Локальная резервная копия может исчезнуть вместе с очисткой данных браузера.

JSON нужен для резервирования и переноса, а не для каждого обновления интерфейса.
Полное восстановление Sport заменяет журнал с предварительным просмотром
и возможностью отмены; это пока не объединение старых и новых записей.

## Отчёты Meal

CSV, PDF и PNG формируются локально из дневника. Они не публикуются в репозитории
и не загружаются на сервер отчётов. CSV содержит все продукты и доступный состав
за выбранный период; для PDF, PNG и печати состав выбирается галочками.
Перед отправкой можно посмотреть страницы. Системное «Отправить PDF» передаёт
файл только тому приложению/получателю, которого выберет сам пользователь.
Эти выгрузки — копии личных данных, не замена полному резерву JSON.

## Общие замеры тела

Один интерфейс Sport встроен в журналы Day и Meal. Локальный документ:
`happy-measurements-v1:<uid>`; без входа — суффикс `local`. Старая копия дневника
Sport не удаляется. Однократная миграция относит записи к сохранённому `sportOwner`;
при отсутствии владельца они остаются локальными. Для добавления таких записей
в аккаунт есть отдельная кнопка; совпадающие даты в профиле сохраняются.

На сервер отправляется только зашифрованный документ замеров (AES-GCM, существующий
ключ Happy), app=sport, kind=measurements. Правила RLS существующей таблицы ограничивают
чтение и запись своим user_id. Сохранение локальное сразу; отправка примерно через
секунду, обновление видимого приложения каждые 15 секунд, при возврате и восстановлении
сети. Наличие связи влияет на задержку; при ошибке записи остаются на устройстве.
Даты объединяются с ревизиями и маркерами удаления, запись на сервер условная (CAS).
Это синхронизация замеров; дневники питания и тренировок полностью не синхронизируются.

## Безопасный импорт Meal · 22.11-test.5

`meal/backup-model.js` проверяет JSON до записи. Дополнение сохраняет текущие
настройки и записи с совпадающими ID (в том числе перенесённые между датами),
добавляет недостающие записи и архив. Две одинаковые порции с разными ID остаются
двумя порциями. Архивные строки без ID объединяются с сохранением количества
одинаковых строк; повторная загрузка не удваивает архив.

Полная замена требует отдельного подтверждения. `hdm_db_prev_v1` содержит
дневник перед последним импортом; кнопка возврата остаётся в настройках.
Копия и новый дневник должны успешно записаться в постоянное хранилище;
при ошибке квоты перезапуск не выполняется. Следующий успешный импорт обновляет
эту единственную копию для отмены.

Полный объект DB, включая `importedHistory`, читается при запуске и входит
в экспорт. Исходная метка профиля из файла хранится как `backupProfile`,
возвращается в JSON и не создаёт аккаунт. Разные составы продукта для новой
порции блокируют дополнение; для совпадающих записей побеждает текущая правка.

## Связанные счётчики еды · Meal 22.11-test.8 / Day 50.11

`shared/food-counters.js` хранит только явно связанные счётчики и их порции. Локальный документ — `happy-food-counters-v1:<uid>` (без входа — `local`), незавершённые операции — отдельные ключи `:pending:`. Копия документа включается в JSON дневника как `mealCounters`. По тому же origin изменения доступны второму приложению без входа; между доменами и отдельными хранилищами нужен один аккаунт Happy.

В существующей `app_sync` используется app=meal, kind=counters, с прежним AES-GCM и владельцем из UID. Применяются существующие RLS; серверная схема не менялась. При конфликте запись перечитывается и объединяется, а не заменяется вслепую. Удалённые порции сохраняют маркеры удаления. Обычные счётчики Day и несвязанные продукты Meal не отправляются этим механизмом. Сводка калорий Day обновится, когда Meal получит новые порции и опубликует свою обычную сводку.

Синхронизация работает при открытом приложении, при возврате и восстановлении сети. Закрытая веб-страница не выполняет фоновый обмен. Ошибки показываются под счётчиками; локальные нажатия сохраняются. Это не полная синхронизация дневников. Ограничение существующей серверной строки (4 млн символов шифротекста) обрабатывается сообщением об ошибке, без удаления записей.

# Работа с Happy — правила для исполнителей

Единственный файл правил репозитория. Читать первым. Остальные документы отвечают каждый за своё и правил не дублируют:

- `APPS.md` — карта приложений: выпуски, версии, адреса, где лежит код.
- `CHANGELOG.md` — что выпущено, с проверками и ограничениями. Новые записи сверху.
- `DATA-STORAGE.md` — где хранятся данные, синхронизация, резервные копии.
- `LIBRARIES.md` — предложения для справочников (упражнения, продукты, иконки); «к добавлению» не значит «есть в приложении».
- `shared/README.md` — общие элементы интерфейса и их сборка.

- **Подпись.** Каждая запись в `CHANGELOG.md` и каждый изменённый раздел в `APPS.md`, `AGENTS.md`, `LIBRARIES.md`, `DATA-STORAGE.md`, README выпусков заканчивается строкой `— Имя · ДД.ММ.ГГГГ ЧЧ:ММ` (время по Москве): `— Claude · 09.11.2026 11:40`. - **Статусы.** «Сделано» ставит исполнитель со ссылкой на выпуск или коммит; «проверено» — только Астамур после проверки на iPhone. Планы не выдавать за выпущенные функции.
- Один исполнитель на задачу; не брать строку доски, которая «в работе» у другого.

## Репозиторий и ветки

- Перед работой получить свежий `main`, прочитать `APPS.md` и `DATA-STORAGE.md`. Работать в отдельной ветке задачи; не затирать параллельные изменения, не делать force push; перед слиянием проверить изменения коллег.
- Теги не ставятся (решение владельца от 08.11.2026): выпуск опознаётся по имени апдейта в каталоге, в приложении, в `shared/apps.json`, в `APPS.md` и в `SOURCE-PROVENANCE.json` выпуска.
- Актуальные входы: `day-55/index.html`, `meal-26/index.html` (26.1), `sport-39/index.html`; `day/`, `day-52/`, `day-53/`, `day-54/`, `meal/`, `meal-23/`, `meal-24/`, `meal-25/`, `sport/`, `sport-37/`, `sport-38/` — сохранённые прежние версии.
- Старые HTML в корне — исторические файлы или переходы; не развивать их как текущие версии.
- Сохранять постоянные URL, ключи хранилища и пользовательские записи. Изменения схемы требуют миграции.
- Личные выгрузки и журналы, токены и ключи нельзя коммитить. Публичные справочники не являются дневниками.
- В корне лежит `.nojekyll`: GitHub Pages копирует файлы без обработки Jekyll — не удалять. Pages публикует корень `main`; новые папки работают под префиксом `/happyamurio/`. Лимит публикаций около 10 в час — правки выкладывать пачками.
- Sites — отдельная рабочая копия и отдельный домен, автоматического обмена с GitHub нет. Перед работой через Sites брать свежий код отсюда; переносить обратно только изменения задачи; не заменять Day и Meal устаревшими копиями из Sites. Адрес Sites не превращается в GitHub Pages при переносе, данные браузера не переносятся.

## Выпуски

- Для нового согласованного апдейта создавать отдельный каталог из выбранной исходной версии (`day-52/` → `day-53/`). Sport собирать из исходников в каталог нового выпуска; не перезаписывать опубликованные сборки побочным результатом сборки. Коммитится только корень выпуска (`index.html`, `exercises/`, `data/`, `app-icons/`, manifest) и исходники; промежуточные результаты сборки (`dist/`, `sport/dist/`, копии иконок в `sport/`) в `.gitignore` и пересобираются локально. Перед `npm --prefix sport-NN/sport run check` на свежей копии сначала `node sport-NN/scripts/build-release.mjs`. `index.html` выпуска Sport вручную не править.
- При выпуске обновить видимую версию, `shared/apps.json`, `APPS.md` и `CHANGELOG.md` в одном изменении. В `CHANGELOG` указать дату, версии затронутых приложений, H-номера задач, добавления/исправления, выполненные проверки, оставшиеся ограничения и подпись. Личные данные не включать. Для изменений только документации версии приложений не повышать. История кода — Git.
- Небольшие исправления обозначать номером после точки: Sport 38.1, затем 38.2.
- Начиная с Happy Meal Update 23 новые выпуски используют общие самостоятельные пищевые библиотеки из ветки `meal-libraries`. Старые выпуски не переделывать. Сохранённые документы питания не пересчитывать при обновлении справочников.

### Публикация согласованных апдейтов · правило владельца от 07.11.2026

- Каждый новый согласованный апдейт публиковать отдельно, под согласованным именем/номером и по собственному URL GitHub Pages. Имя апдейта должно быть видно в приложении и записано в карте версий.
- Основной сайт, ранее опубликованные выпуски и их адреса сохранять. Не заменять их содержимое и не перенаправлять на новую версию без прямого указания владельца. Новая ветка сама по себе не является опубликованной страницей.
- Закреплять зависимости и scope установки за новым выпуском, чтобы его изменения не меняли старые страницы. Ключи пользовательских данных, аккаунты и облачные документы от смены адреса самовольно не менять.
- После отправки кода дождаться успешного размещения GitHub Pages и открыть точный полный URL. Проверить видимое имя/номер версии. Различать «код сохранён», «публикация идёт/не удалась» и «версия опубликована»; ссылку давать целиком.

## Общие библиотеки

- Картинки занятий Sport лежат один раз в неизменяемой библиотеке `assets/sport-icons/v1/` (постоянный адрес, подключается в `sport/scripts/build.mjs` через `SPORT_ICON_LIBRARY`); файлы внутри `v1/` не менять — изменённый набор идёт в новую папку `v2/`, на которую переключается следующий выпуск. - Справочник упражнений, оборудования и групп мышц Sport — `assets/exercise-library/v1/` (`exercises.json`, `equipment.json`, `exercise-muscles.json`, `manifest.json` с хешами). Проверки читают справочник только через `seed.mjs`.

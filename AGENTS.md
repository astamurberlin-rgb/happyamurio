# Работа с Happy

- Главные инструкции: `APPS.md` и `DATA-STORAGE.md`. Прочитать до изменения приложений.
- Актуальные входы: `day-52/index.html`, `meal-23/index.html`, `sport-37/index.html`; `day/index.html` — сохранённая прежняя версия.
- Для нового согласованного апдейта создавать отдельный каталог из выбранной исходной версии. Sport собирать из исходников в каталог нового выпуска; не перезаписывать опубликованные сборки побочным результатом сборки.
- Старые HTML в корне — исторические файлы или переходы; не развивать их как текущие версии.
- Сохранять постоянные URL, ключи хранилища и пользовательские записи. Изменения схемы требуют миграции.
- Личные выгрузки и журналы, токены и ключи нельзя коммитить. Публичные справочники не являются дневниками.
- Перед работой обновить main, использовать ветку задачи, не затирать параллельные изменения.
- Sites не синхронизируется автоматически: сверять с main до и после работы.
- Проверки: `npm --prefix sport run build`, `npm --prefix sport run check`, `node scripts/check-layout.mjs`.
- При выпуске обновить видимую версию, `shared/apps.json` и `CHANGELOG.md` в одном изменении. В CHANGELOG указать дату, версии затронутых приложений, добавления/исправления, выполненные проверки и оставшиеся ограничения. Планы не выдавать за выпущенные функции; личные данные не включать. Для изменений только документации версии приложений не повышать. История кода — Git.
- Небольшие исправления обозначать номером после точки: например, Sport v36.1, затем v36.2.
- Общие элементы интерфейса менять в `shared/happy-ui.css` и `shared/happy-ui.js`, образец — Happy Meal. Затем `node scripts/sync-shared-ui.mjs` и сборка Sport. Проверить `node scripts/check-shared-ui.mjs`.
- Общие функции сохраняют одинаковые названия и порядок: аккаунт, резервная копия, связанные приложения; версия всегда в самом низу. Иконка настроек — шестерёнка.

## Публикация согласованных апдейтов · правило владельца от 07.11.2026

- Каждый новый согласованный апдейт публиковать отдельно, под согласованным именем/номером и по собственному URL GitHub Pages. Например: `day-52/`, затем `day-53/`. Имя апдейта должно быть видно в приложении и записано в карте версий.
- Основной сайт, ранее опубликованные выпуски и их адреса сохранять. Не заменять их содержимое и не перенаправлять на новую версию без прямого указания владельца. Новая ветка или тег сами по себе не являются отдельной опубликованной страницей.
- Закреплять зависимости и scope установки за новым выпуском, чтобы его изменения не меняли старые страницы. Ключи пользовательских данных, аккаунты и облачные документы от смены адреса самовольно не менять.
- Обновлять `APPS.md`, `shared/apps.json` и `CHANGELOG.md` с именем и отдельным адресом выпуска, сохраняя сведения о прежних версиях.
- После отправки кода дождаться успешного размещения GitHub Pages и открыть точный полный URL. Проверить видимое имя/номер версии. Различать «код сохранён», «публикация идёт/не удалась» и «версия опубликована»; ссылку давать целиком.


- Начиная с Happy Meal Update 23, новые выпуски используют общие самостоятельные пищевые библиотеки из ветки `meal-libraries`. Старые выпуски не переделывать. Сохранённые документы питания не пересчитывать при обновлении справочников.

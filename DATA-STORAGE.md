## После обновления

Перенос сохраняет существующий формат и адреса хранения записей.
В том же браузерном хранилище новые страницы должны читать прежние записи.
Другой домен, браузер, устройство или установленная иконка могут использовать
другое хранилище. До удаления старой иконки проверить дневник на новом адресе.
Локальная резервная копия может исчезнуть вместе с очисткой данных браузера.

JSON нужен для резервирования и переноса, а не для каждого обновления интерфейса.
Полное восстановление Sport заменяет журнал с предварительным просмотром
и возможностью отмены; это пока не объединение старых и новых записей.

## Отчёты Meal

CSV, PDF и PNG формируются локально из дневника. Они не публикуются в репозитории
и не загружаются на сервер отчётов. CSV содержит все продукты и доступный состав
за выбранный период; для PDF, PNG и печати состав выбирается галочками.
Перед отправкой можно посмотреть страницы. Системное «Отправить PDF» передаёт
файл только тому приложению/получателю, которого выберет сам пользователь.
Эти выгрузки — копии личных данных, не замена полному резерву JSON.

## Что дальше

Отдельный этап — полная автоматическая синхронизация, работа без сети,
обработка конфликтов и импорт истории без дублей и потери ручных записей.
Выгрузки Apple Health, Strong и Cronometer в этом шаге не импортировались.

## Общие замеры тела

Один интерфейс Sport встроен в журналы Day и Meal. Локальный документ:
`happy-measurements-v1:<uid>`; без входа — суффикс `local`. Старая копия дневника
Sport не удаляется. Однократная миграция относит записи к сохранённому `sportOwner`;
при отсутствии владельца они остаются локальными. Для добавления таких записей
в аккаунт есть отдельная кнопка; совпадающие даты в профиле сохраняются.

На сервер отправляется только зашифрованный документ замеров (AES-GCM, существующий
ключ Happy), app=sport, kind=measurements. Правила RLS существующей таблицы ограничивают
чтение и запись своим user_id. Сохранение локальное сразу; отправка примерно через
секунду, обновление видимого приложения каждые 15 секунд, при возврате и восстановлении
сети. Наличие связи влияет на задержку; при ошибке записи остаются на устройстве.
Даты объединяются с ревизиями и маркерами удаления, запись на сервер условная (CAS).
Это синхронизация замеров; дневники питания и тренировок полностью не синхронизируются.

## Разделение локальных профилей

`shared/profile-storage.js` связывает ключи дневника, настроек, обмена и отмены импорта с UID аккаунта. Общий ключ входа `hd_cloud_v1` остаётся прежним. Анонимный журнал сохраняет прежние ключи; новый аккаунт начинает с отдельного журнала. При первом запуске новой версии прежний журнал с сохранённым входом копируется в область этого владельца, исходные записи не удаляются. У Sport учитывается старый `sportOwner`.

Переход между аккаунтами не переносит записи. Для переноса нужно войти в целевой профиль и загрузить его JSON. Полное восстановление заменяет только журнал этого профиля с копией для отмены. Исходная история импорта хранится в `importedHistory` и включается в последующие JSON-резервы; дневные сводки Cronometer показаны отдельно, без повторного прибавления к продуктам Meal.

## Имя аккаунта · 30.10.2026

Имя/псевдоним необязательны, хранятся в Supabase Auth user_metadata.display_name. Одинаковый профиль доступен во всех приложениях после входа. Изменение имени не меняет UID, дневник, пароль и ключ шифрования. Вход/регистрация и редактирование имени разделены. Офлайн имя не сохраняется на сервер: форма оставляет черновик и показывает ошибку.

## Связанные счётчики еды · Meal 22.14 / Day 50.11

`shared/food-counters.js` хранит только явно связанные счётчики и их порции. Локальный документ — `happy-food-counters-v1:<uid>` (без входа — `local`), незавершённые операции — отдельные ключи `:pending:`. Копия документа включается в JSON дневника как `mealCounters`. По тому же origin изменения доступны второму приложению без входа; между доменами и отдельными хранилищами нужен один аккаунт Happy.

В существующей `app_sync` используется app=meal, kind=counters, с прежним AES-GCM и владельцем из UID. Применяются существующие RLS; серверная схема не менялась. При конфликте запись перечитывается и объединяется, а не заменяется вслепую. Удалённые порции сохраняют маркеры удаления. Обычные счётчики Day и несвязанные продукты Meal не отправляются этим механизмом. Сводка калорий Day обновится, когда Meal получит новые порции и опубликует свою обычную сводку.

Синхронизация работает при открытом приложении, при возврате и восстановлении сети. Закрытая веб-страница не выполняет фоновый обмен. Ошибки показываются под счётчиками; локальные нажатия сохраняются. Это не полная синхронизация дневников. Ограничение существующей серверной строки (4 млн символов шифротекста) обрабатывается сообщением об ошибке, без удаления записей.

Определения общих продуктовых счётчиков содержат независимые targets.day и targets.sport. Старое определение без targets связано только с Day. ## Дневник активности · Day 50.13

Настройки, дневники, цели и расписание находятся в `DB.selfCare`, отметки самочувствия/события дневника/практики — в `DB.days[date].care`, в прежнем профильном ключе Day. Новое открытие самочувствия создаёт новую отметку; жесты внутри одного открытия обновляют её. Пустое открытие не записывается. Прежние разделы дня и записи текущего состояния сохраняются. Формат повышен с 47 до 49: старая версия не может перезаписать новые поля. Эти данные включены в полный JSON; автоматическая синхронизация всего дневника не добавлена. Данные отдельного домена прототипа не переносятся автоматически.

Связь с Strong/Sport читает план и краткие факты из выбранного JSON-резерва или существующей зашифрованной облачной копии sport/journal. Это не непрерывная синхронизация расписания. Настройки видимости не удаляют историю.

## Color Studio · облако тем · 06.11.2026

Color Studio 12.7 по желанию сохраняет «Мои варианты оформления» в Supabase. Вход выполняется тем же аккаунтом Happy, но в отдельной сессии студии под ключом `happy_studio_cloud_v1`. Общий ключ `hd_cloud_v1` студия не читает и не меняет. Выход из студии использует `logout?scope=local`, поэтому входы Day, Meal и Sport не завершаются.

Данные хранятся в отдельной таблице `public.studio_sync` (studio=`color`, kind=`themes`), а не в `app_sync`. Day, Meal и Sport эту таблицу не читают. Схема и правила RLS лежат в `supabase/studio_sync.sql`.

В облако уходят темы без фото: `wallpaperData` остаётся на устройстве, в облаке только признак `photo`. Туда же уходят время изменения каждой темы и отметки удаления `deletedThemes`, они хранятся 180 дней. Темы объединяются по одной: побеждает более поздняя правка, а удаление побеждает правки, сделанные до него. Запись условная по `rev`. При конфликте студия перечитывает документ, объединяет и повторяет запись.

Темы не шифруются, это настройки оформления. Доступ к ним ограничен своим user_id через RLS. Палитры, текущий вид превью и фото пока хранятся только на устройстве. Оба входа студии (`studio.html` и v12) используют один облачный документ.

С Color Studio 12.8 и Icon Studio 2.17 вход общий для обеих студий. Кнопка входа стоит в шапке, код лежит в модуле `shared/happy-studio-account.js`, в `icon-studio/` его точная копия. Icon Studio пока не отправляет данные в облако, её работа хранится на устройстве.

Внутри каждого Web Lock адаптер перечитывает ключи из IndexedDB после захвата и ждёт `flush()` перед освобождением; «страховочная копия сохранена» говорится только после фиксации в IndexedDB. Проба места в localStorage в IndexedDB не выполняется (оценка `navigator.storage.estimate()`, настоящий ответ даёт сама запись). Общий localStorage сайта (~5 МБ на все три приложения) после Day 56 почти свободен.
